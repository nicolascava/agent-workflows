---
name: pr
description: Create a pull request for the current feature branch after verification and visible-description checks. Use only in PR workflow mode.
---

Requires `core` for `/core:verify`. Read `${CLAUDE_PLUGIN_ROOT}/docs/safety.md`, `${CLAUDE_PLUGIN_ROOT}/docs/workflow-modes.md` and `${CLAUDE_SKILL_DIR}/../../docs/pr-copy.md`.

1. Inspect the branch, worktree, remote and any existing PR read-only. Resolve mode. In `solo-shaped-kanban`, refuse PR creation and point to `/core:review` then `/git-flow:land`. Missing or unknown mode blocks creation and shows the setup message. Require an owned feature branch, clean tree and no in-progress Git operation. If a PR already exists, report it and use `/git-flow:update-pr` for metadata changes.
2. Confirm the explicit target repository and base branch. Fetch that branch with `verification-source.ts`, pin full base/HEAD/tree OIDs and inspect the actual diff. Do not draft from a commit subject or stale local base alone. If the work contains dependent reviewable layers, read `${CLAUDE_PLUGIN_ROOT}/docs/stacked-prs.md`, propose the stack and obtain approval before creating multiple branches or PRs. A stack is optional.
3. Run `/core:verify` using the repository's commands. Check for valuable missing behavior tests. Add or fix them only within the authorized task scope, then commit the changes and rerun affected gates. Do not add tests that merely mirror trivial implementation. Require relevant checks to pass before creation; report any evidence that cannot be collected.
4. Read any issue the user supplied, including its repository and acceptance requirements. Follow the target repository's issue policy. An issue is optional unless that policy requires one. Keep canonical issue URLs non-closing unless the user explicitly asks to close. If `issues` is installed, it may assist with an issue under its own authority. Do not perform project-specific Development lookups, reviewer identity guesses or automatic issue-state changes.
5. Prepare the exact title and visible body in unique temporary files using the copy doc. Include only verified checkboxes and concrete deferred steps. If `specialists` is installed and provides a copy editor, that review is optional. Run `check-pr-copy.ts` and any repository copy checks on the final files. A copy edit never grants mutation authority. If an optional creation guard hook is installed, follow its documented path; this batch has no guard-authorize step or marker store.
6. Recheck the mode, destination, base and HEAD. Confirm the requested PR creation and branch push are within scope. Push only the feature branch with a normal explicit refspec, never the base. Verify the remote feature OID equals the checked HEAD. If an existing PR appears during the run, stop and inspect it instead of creating a duplicate.
7. Create with `gh pr create -R <repository> --base <base-branch> --head <feature-branch> --assignee @me --title <exact-title> --body-file <body-file>`. Supply the title safely as an argument, not an interpolated shell command. Read back the PR's repository, head, title and complete body. Stop on mismatch; report any created PR even if readback fails. Do not merge or post a review as part of creation.
8. Report the PR URL, pinned source OIDs, push and verification results, issue reference or reason none was required, copy-check result and any pending evidence. Stop after creation and readback.
