---
name: rebase
description: Rebase an authorized feature branch onto a freshly fetched base, resolve conflicts by intent, verify, and push only when that rewrite is authorized.
---

Requires `core` for `/core:verify`. Read `${CLAUDE_PLUGIN_ROOT}/docs/safety.md` and `${CLAUDE_PLUGIN_ROOT}/docs/workflow-modes.md`. Works in both modes. Do not create or merge a PR, land or change PR metadata.

1. Inspect the physical worktree, current branch, status and ongoing Git operations. Refuse detached HEAD, the delivery base and a dirty tree. Do not stash or discard automatically. If a rebase is already in progress, use `/git-flow:resolve-conflicts` to continue its authorized scope; do not start another rebase.
2. For a PR, resolve its explicit repository, author, actor, head repository/branch/OID and actual base. Apply the author gate before checkout or branch mutation; refuse fork branch mutation. Require the local branch to match the PR head before rewriting. For branch-only work, verify ownership or exact authority. In solo mode, no PR is needed.
3. Resolve the requested base from repository guidance and the mode declaration. A missing mode does not prevent an authorized local rebase, but the base must be explicitly resolved and fetched. Run `verification-source.ts --base <branch> --remote <remote>` and retain full base and old HEAD OIDs. If a push is authorized, fetch the feature branch too and pin its exact remote OID before rewriting. Do not derive a lease from a tracking ref that may refresh later. Confirm the fetched feature OID equals the old HEAD, or stop to reconcile.
4. Run `git rebase <baseOid>`, using the immutable fetched commit. For conflicts, read the file, upstream changes, replayed commit and tests. Preserve both intended behaviors. During a rebase, ours means the upstream plus replayed commits; theirs means the commit being replayed. Do not choose a side blindly. Stage only resolved paths and continue. Keep hooks enabled.
5. Apply `/git-flow:resolve-conflicts` for conflicts. Stop after three failed resolution or continuation cycles, an ambiguous requirement, or a required gate that cannot pass. Report the current Git state and leave it for the user; do not abort or reset automatically. If generated files need regeneration, use only the target repository's documented command within scope.
6. Run `/core:verify` after the completed rebase. Require relevant gates to pass. Report changed commits with `git range-diff <old-base>..<old-head> <new-base>..<new-head>` when the old base can be verified. Do not invent an old base or claim a hash-only rewrite proved equivalent. Any previous review is stale after a rewritten HEAD and must be refreshed before landing or merging.
7. Push only if the user's scope includes updating the feature branch. Recheck mode where delivery-dependent, author, actor, branch and destinations. Use `git push <remote> HEAD:refs/heads/<feature-branch> --force-with-lease=refs/heads/<feature-branch>:<old-remote-oid>` for an authorized rewrite. Never push to the base or use bare force. A failed lease stops the operation; do not refresh it and retry over someone else's work. With no push authority, leave the local result and report it.
8. Report old/new HEAD, fetched base, lease OID, conflicts and reasoning, commands and gates, push status and remaining work. Do not claim the PR is merged.
